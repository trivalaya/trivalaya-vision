# Transparent PNG Resize (cap at 518px longest side)

Resize all alpha-masked transparent PNGs (auction + PCO) to a maximum
longest-side of 518 pixels at storage time. Source JPEGs are
unaffected and remain the authoritative pixels.

Owner: vision / pipeline plumbing
Status: spec — not yet implemented
Date: 2026-05-27

---

## Why

The transparent PNGs exist solely to feed DINOv2 (via
`cluster_coins.open_image_masked`, composited on grey). DINOv2
variants take 224 / 336 / 518-pixel inputs. The current pipeline
stores full-resolution masked PNGs (often 3000-4000px), and the GPU
run on RunPod then:

1. Downloads the full-size PNG (bandwidth — real money on RunPod
   egress).
2. Resizes to the model's input dimension on the GPU.
3. Embeds.

Resizing at storage time instead means smaller downloads, no
GPU-side resize, and a one-time storage reduction. The full-res
source JPEGs (`*_obv.jpg` / `*_rev.jpg`) are preserved, so the
high-res transparent can be regenerated at any time by re-running L1
+ `crop_with_alpha`.

---

## Cap choice: 518px longest side

- Matches DINOv2-giant native input (518) exactly — no GPU-side
  resize at all when the giant model is the consumer.
- Comfortably above DINOv2-base (224) and DINOv2-large (336); those
  downsize once at inference, same as today.
- If a future embedding model needs ≥768px input, re-pilot with a
  larger cap; don't ratchet 518 → 1024 speculatively.

**Resize policy:**
- `cv2.INTER_AREA` for downscale (correct choice for shrinking;
  Lanczos can ring on hard edges, alpha included).
- Alpha channel resized with the same interpolator as RGB.
- If the image's longest side is already ≤ 518, no resize — write
  the original bytes through unchanged.
- Preserve aspect ratio: scale by `518 / max(H, W)`.

## Scope

Two populations of transparents to consider:

1. **Auction transparents** — already exist in Spaces, full-res. Need

2. **PCO transparents** — generated by the new worker in
   `specs/pco_transparent_generation.md`. The PCO worker must emit
   518-cap from day one, not full-res. Spec update referenced in §6.

## Storage savings (measured, not estimated)

Numbers below come from the 2026-05-27 bucket scan documented in
`specs/spaces_usage_baseline.md` §4 and §7. Refer to that doc for
the full size histogram and the methodology.

**Current state:** 589k transparent PNGs, **502 GB total**, avg 833 KB.

**Empirical compression ratio:** ~1.75 KB per 1000 pixels for these
alpha-masked coin PNGs (high-entropy engravings + alpha channel).

**Post-518-cap per object:** 518² × 1.75 ≈ **~470 KB** (not the
160–320 KB initially assumed).

**Bucket-by-bucket projection** (from baseline doc §7):

| bucket | objects | current GB | post-resize GB | savings GB |
|---|---|---|---|---|
| 0–500 KB (≤~500px) | 110k | 30.8 | 30.8 (no-op) | 0 |
| 500–1000 KB (~600–700px) | 384k | 293.4 | ~180 | ~113 |
| 1000–2000 KB (~825–1000px) | 71k | 95.0 | ~33 | ~62 |
| 2000+ KB (~1200px+) | 24k | 82.9 | ~11 | ~72 |
| **Total** | **589k** | **502** | **~255** | **~247** |

**Net: 502 GB → ~255 GB. Savings ~247 GB (~49% of the prefix, ~28%
of the total bucket).**

The savings are bimodal: roughly half come from the 384k objects in
the 500–1000 KB band (modest per-object win, big aggregate), the
other half come from the 24k objects in the >2 MB tail (huge
per-object win on a small population). The 110k objects already
under ~500 KB no-op — they're already at or below 518px.

Re-measure post-migration by re-running the histogram script
(`specs/spaces_usage_baseline.md` §8). Persist the result in
`specs/transparent_resize_baseline.json` so the actual delta is
auditable.

## Pilot (20 coins)

**Frozen, reproducible.** Same pattern as the PCO pilot — pick 20
auction coin IDs once, commit them to `specs/transparent_resize_pilot_ids.csv`
(columns: `id, side, transparent_key`). Re-pilots run the same 20.

Stratify across coin-dimension buckets (resize cost varies with
input size):

- 7 × small auction crops (longest side ≤ 1500px) — these get a
  no-op pass, validates the short-circuit path
- 7 × medium (1500-3000px)
- 6 × large (>3000px)

**Pilot procedure** per side:

1. Download the existing full-res transparent.
2. Resize to 518-cap per §2.
3. Composite both versions on grey (`open_image_masked` recipe).
4. Embed both via DINOv2 — full-res and resized — using the canonical
   embedding script.
5. Compute cosine distance between the two embeddings.

**Exit criterion:** ≥18/20 sides have cosine distance ≤ 0.005
between full-res and 518-cap embeddings. If drift exceeds that,
investigate before bulk — likely an interpolation or alpha-handling
bug.

This pilot is fast: no L1, no rim recovery, just resize + embed.
Should take an hour wall time.

## Bulk migration — `tools/resize_transparents.py`

New file (this is a tooling job; lives in `tools/`, not the pipeline
package).

**Startup:**
- Same thread caps as the PCO worker: `OMP_NUM_THREADS=1`,
  `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1` before importing
  cv2/numpy. `cv2.setNumThreads(0)` after.
- ACL discovery (same approach as PCO worker): read one existing
  transparent's ACL grants, reuse for every PUT.

**Row selection** (resumable via key-suffix rename, not via DB
column):

The migration writes the resized PNG to a versioned sibling key:
`*_transparent.png` → `*_transparent_v2.png`. Then updates the DB
pointer (`coin_detections.transparent_path` or
`collection_data.{obv,rev}_transparent_path` for PCO) to point at
the new key. The original `*_transparent.png` is left in place
during the migration; a GC sweep deletes them after the confidence
window (§7).

This is much safer than in-place overwrite: rollback is just
"revert the DB pointer."

```sql
-- Auction side
SELECT id, transparent_path
FROM coin_detections
WHERE transparent_path IS NOT NULL
  AND transparent_path NOT LIKE '%_v2.png'
ORDER BY id;

-- PCO side (after the PCO worker has populated columns; tackle separately)
SELECT id, obv_transparent_path, rev_transparent_path
FROM collection_data
WHERE collection_id='pco'
  AND ((obv_transparent_path IS NOT NULL AND obv_transparent_path NOT LIKE '%_v2.png')
    OR (rev_transparent_path IS NOT NULL AND rev_transparent_path NOT LIKE '%_v2.png'));
```

**Per object:**
1. HEAD the v2 dst key. If it exists, skip upload, just update DB
   pointer.
2. Download the original transparent; `cv2.imdecode` with
   `cv2.IMREAD_UNCHANGED` (preserves alpha).
3. If `max(H, W) ≤ 518`, write original bytes through to v2 key
   (no re-encode — avoids unnecessary PNG round-trip).
4. Otherwise resize per §2.
5. `cv2.imencode(".png", resized, [cv2.IMWRITE_PNG_COMPRESSION, 6])`.
6. `s3.put_object(..., Grants=<from startup>)` to v2 key.
7. Update DB pointer: `UPDATE … SET transparent_path = :v2_key WHERE id = :id`.

**Observability** (same as PCO worker): emit a counter line every
100 rows or 60s — `processed=N noop=N resized=N skipped=N`.

**Workers:** 16 default. Network-bound on Spaces; CPU-bound on
PNG decode/encode. Same scaling envelope as PCO worker and
`tools/reprocess_hough.py`.

**DB concurrency:** partition rows by `id MOD workers` so two
workers never touch the same row. No SELECT … FOR UPDATE needed.

## Acceptance

### 7a. Coverage gate

```sql
SELECT COUNT(*) FROM coin_detections
WHERE transparent_path IS NOT NULL AND transparent_path NOT LIKE '%_v2.png';

SELECT COUNT(*) FROM collection_data
WHERE collection_id='pco'
  AND ((obv_transparent_path IS NOT NULL AND obv_transparent_path NOT LIKE '%_v2.png')
    OR (rev_transparent_path IS NOT NULL AND rev_transparent_path NOT LIKE '%_v2.png'));
```

Both must return 0 (no skip list — every transparent gets resized;
there's no failure mode beyond "download failed" which is retried on
resume).

### 7b. Storage gate

Re-run the measurement from §3 against the `_v2.png` set and the
remaining `_transparent.png` set. Report:

- v2 total GB
- old total GB
- savings ratio

Expected ratio: v2 / old ≈ 0.5 (savings ~50%, per §3 projection). If
the actual ratio is materially worse (e.g., v2 / old > 0.7),
investigate — most likely cause is a higher than expected fraction
of already-≤518px input objects that no-op.

### 7c. Embedding-equivalence gate (sample)

Pick 50 random auction sides post-migration. Embed via DINOv2 using
the v2 transparent. Compare to a fresh embedding generated from the
preserved source JPEG by running L1 + `crop_with_alpha` + 518-cap
resize inline. Cosine distance ≤ 0.005 on ≥ 95% of pairs.

This catches "did the migration silently corrupt anything" without
needing to keep the pre-migration features.npy around.

## GC sweep (deferred, separate PR)

After **30 days** of the new v2 keys being in production with no
regression reports:

```bash
# Dry-run list every *_transparent.png whose sibling *_transparent_v2.png exists
# Confirm count matches expected
# Then delete in batches of 1000 with --confirm
```

Don't combine the GC with the migration. The point of the v2-suffix
approach is that rollback during the confidence window is a
DB-pointer revert; deleting the originals foreclosure-s that
option.

## Risks & mitigations

| risk | mitigation |
|---|---|
| Embedding drift from interpolation differences | Pilot (§4) gates the bulk; cosine ≤ 0.005 |
| Debug/viz tools expecting high-res transparents | Source JPEGs preserved; regenerate via L1 + crop_with_alpha when needed |
| Concurrent migration vs. live pipeline reads | v2-suffix approach — old key stays valid until DB pointer updates; reads never see a missing object |
| Bucket policy / ACL drift | ACL discovery copies grants from an existing object, not asserted |
| Accidentally resizing already-resized v2 objects on retry | Selection query filters `NOT LIKE '%_v2.png'`; HEAD-before-upload short-circuit on the worker side |
| Larger-input model adopted later (≥768px) | Re-pilot at a larger cap; sources still exist, so re-migration is just another pass |

## Rollback

If §7c flags drift or downstream consumers report regressions:

1. **Revert DB pointers:**
   ```sql
   -- For each affected row, set transparent_path back to the
   -- original key (strip the _v2 suffix).
   UPDATE coin_detections
   SET transparent_path = REPLACE(transparent_path, '_transparent_v2.png', '_transparent.png')
   WHERE transparent_path LIKE '%_transparent_v2.png';
   -- Same shape for collection_data.{obv,rev}_transparent_path.
   ```
2. The original `*_transparent.png` objects are untouched (no GC has
   run during the confidence window) — reads resume working
   immediately.
3. Leave the v2 objects in place pending diagnosis; GC them later
   if the migration is abandoned.
4. Investigate the failing pair from §7c.

Fully reversible during the 30-day confidence window. After GC
sweep, only the v2 versions remain — re-migration would require
regenerating from source JPEGs (still doable, just slower).

## Related: outlier-cap policy for source images and crops

Not part of this spec's bulk migration — captured here as a follow-up
because the baseline measurement surfaced the opportunity, and the
v2-suffix + worker pattern from §5 generalizes cleanly. Track this as
its own spec when work begins; the section below is a pointer, not
an approved plan.

### Why

`specs/spaces_usage_baseline.md` §3 and §6 surfaced two
prefixes worth attacking after the transparent migration:

| population | size | per-object distribution |
|---|---|---|
| `raw/auctions/` (raw lot photos) | 105 GB | p50 274 KB, p95 813 KB, p99 1578 KB, **max 47.7 MB** |
| `processed/.../crop.jpg` (single-coin JPG crops) | 110 GB | p50 166 KB, p95 373 KB, p99 708 KB, **max 4.7 MB** |

The distributions are dominated by a small heavy tail. The median raw
is 274 KB (typical 1200×~600 2-coin lot photo). The p95 is 813 KB.
The max is **47 MB** — a single object two orders of magnitude
above the median.

A blanket 518-cap on raws doesn't make sense (L1 needs the source
resolution to find rims). But pulling the extreme tail toward the
distribution's center is essentially free of fidelity cost on the
content that matters.

### Policy

For raws and crops, the proposed heuristic is:

1. Measure the longest-side dimension distribution (not byte
   distribution — see "Caveat" below).
2. **Cap = p95 of longest-side.** Anything ≤ cap is untouched.
3. **Resize outliers' longest-side to the distribution mean.** Not
   p95 itself; the mean. This is the "snap outliers back to typical"
   policy, not "soft-cap everything just above the line."
4. Use the same v2-suffix-key + DB-pointer-update pattern as §5.

Why mean instead of p95: anything above p95 is a statistical
anomaly, not a graduated case. The interesting question is whether
the anomaly carries useful signal. For raws, the assumption is "no" —
all the L1-relevant content lives at typical dimensions, and the
oversized outliers are scanner artifacts or atypical sources. The
pilot has to validate this assumption per population.

### Caveat: dimension vs byte percentiles diverge

Spot-check from the dimension samples in §5 of the baseline doc:

- raws p95 by **bytes** = 813 KB at 1413×703
- raws p99 by **bytes** = 1578 KB at 1200×574 (smaller dims!)

The byte-heavy tail isn't purely from oversized images — some is
from high-detail content at normal dimensions (JPG quality varies
across auction houses). A pure dimension-cap policy doesn't help
those.

Two ways to address:
- **Layered policy:** cap longest dim at p95-by-dim AND cap JPG
  bytes by re-encoding at lower quality if bytes exceed some
  ceiling. Two knobs, two pilots.
- **Single-pass dim cap only:** simpler, accept that ~10-30% of the
  tail savings are unreachable without a quality drop.

The implementation spec picks one. Start with single-pass.

### Expected savings (rough)

Assuming dim-cap only, applied to the top 5% of each population
resized to the mean longest-side:

| population | top 5% objects | top 5% bytes | post-resize bytes | savings |
|---|---|---|---|---|
| raws (290k total) | ~14.5k | ~29 GB | ~5 GB | **~24 GB** |
| crops (584k total) | ~29k | ~17 GB | ~5 GB | **~12 GB** |
| **combined** | | **~46 GB** | **~10 GB** | **~36 GB** |

These are illustrative. The actual savings depend on the byte
distribution within the top 5%, which is unknown without integrating
the upper tail of the histogram. The 47.7 MB raw outlier alone is
50 GB worth of "what is this?" investigation.

For comparison: the transparent 518-cap (this spec's main payload)
saves ~247 GB. Source-image outlier-resize is meaningfully smaller
but cheaper to implement (no embedding-drift risk because raws
aren't the embedding input — they're upstream of L1).

### Risks specific to source-image resize

- **Lossy upstream of L1.** Resizing a raw or crop discards source
  pixels permanently (modulo the v2-suffix retention period). If a
  future L1 wants to rerun against a higher-fidelity input, we lose
  that option for the top 5%.
  Mitigation: extend the v2-confidence window from 30 days (the
  transparent spec) to **90+ days** for source-image resize.
  Alternatively, keep the original objects forever and just update
  the DB pointer — costs storage but is undo-safe indefinitely.
- **L1 hasn't seen the resized inputs.** Validate by re-running L1
  + crop_with_alpha on a pilot set of resized raws; embeddings must
  match the originals within drift tolerance (~0.005 cosine, same
  bar as the transparent pilot).
- **The 47 MB outlier specifically** is worth manual triage before
  any bulk run — it may be a corrupt upload, a scan-artifact, or a
  legitimate hi-res reference image that someone is using.

### Alternative for crops: delete instead of resize

Resizing crops is only worth doing if crops are actually read. They
serve a single purpose: the rectangular fallback in
`cluster_coins.open_image_masked` when no transparent exists. Once
PCO transparents land (`pco_transparent_generation.md`) and the
518-cap migration completes, every coin in the bucket has a
transparent. The fallback path stops firing.

If that's true, the crops are dead weight, and **deleting them
entirely** beats resizing them — saves the full 110 GB instead of
the ~12 GB from the outlier-resize policy.

**Validation before deleting:**

1. **Grep for crop consumers.** Confirm `cluster_coins.open_image_masked`'s
   `fallback_path` branch is the only reader. Also check viz/debug
   tools, the matcher, any manual-review UI. If anything reads
   `_crop.jpg` outside the fallback, that consumer needs migrating
   first.
2. **Instrument the fallback.** Add a counter in
   `open_image_masked` that logs every fallback miss (record_id,
   side, reason). Run for ~7 days post-migration. If the counter
   stays at 0 outside the documented skip list, the fallback is
   dead.
3. **Then delete.** Same v2-suffix-style confidence window posture:
   first NULL the DB pointers (`coin_detections.fallback_path`
   column or equivalent — verify the schema first), wait ~30 days,
   then delete the S3 objects.

If the counter reveals real fallback usage (e.g., a class of
transparent-failed coins that legitimately use rectangular
embeddings as a documented degraded path), fall back to the
outlier-resize policy above.

### Outlier hotspots from §4c of the baseline doc

The single largest raw (`raw/auctions/obolos/17/Lot_00960.jpg`,
47.7 MB) and 14 of the top 15 outliers live under
`raw/auctions/obolos/{17,19,27}/`. A targeted source-resize pass
against those three sale prefixes would knock out the bulk of the
heavy tail without a full-bucket scan. See `specs/spaces_usage_baseline.md`
§4c for the inspection details and L1-revalidation caveats
(stitched multi-coin plates may behave differently than standard
2-coin lot photos).
